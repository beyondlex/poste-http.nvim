## Bugs fixed

1. **`start_curl_exec` read an undefined global `req_block`** —
   `lua/poste-http/http/run.lua` (surfaced by luacheck as "accessing
   undefined variable"). The function documented `ctx.req_block` as an input
   but never bound the local, so the `meta == nil` fallback (method/url from
   `cache.extract_request_block`) was dead: when tree-sitter describe found
   no block meta, a valid request failed with "Could not determine request
   URL", and request names fell back to "".
   Fix: `local req_block = ctx.req_block`; expose `M.start_curl_exec` for
   tests. Test: `tests/http/run_spec.lua` ("falls back to ctx.req_block…").

2. **`run` directives silently lost their assertion blocks** —
   `lua/poste-http/http/run.lua` (`local _, assertion_code =
   assertions.extract_assertion_blocks(...)` shadowed the outer
   `assertion_code`, so `handle_directive_response` always received nil and
   post-request assertions after a `run` directive never executed).
   Fix: assign the outer variable via `select(2, ...)`, pass the file dir
   like the sibling call site. Test: `tests/http/run_spec.lua`
   ("passes extracted assertion code to handle_directive_response").

3. **`format_request_payload` poisoned the verbose-view cache** —
   `lua/poste-http/http/format/verbose.lua` carried a mangled hunk from
   85d3dbe (`if r then r._cached_verbose = lines end` inside the multipart
   parse-failed branch). Since `format_verbose` early-returns
   `r._cached_verbose`, rendering the Request tab for an unparseable
   multipart body made a later switch to the Verbose tab show the
   request-payload lines instead of the verbose view.
   Fix: restore the plain `return lines` from the pre-85d3dbe code.
   Test: `tests/http/verbose_spec.lua` ("does not poison format_verbose's
   r._cached_verbose…").

4. **Effective URL after redirects showed the first hop** —
   `lua/poste-http/http/response_parser.lua` took the FIRST `Location:`
   match from the curl verbose log; for a redirect chain a→b→c the response
   `url` (verbose view, history) showed b, not the final c.
   Fix: keep the last `Location:` match. Also removed the dead `from`
   heuristics below it (luacheck "value assigned to variable from is
   unused"). Tests: `tests/http/response_parser_spec.lua` ("uses the last
   Location header…", "falls back to the request URL…").

5. **Set-Cookie headers with an empty value were dropped** —
   `lua/poste-http/http/response_parser.lua` matched the cookie value with
   `[^;]+`, so `Set-Cookie: sid=; Path=/` (cookie clearing) discarded the
   whole cookie. Fix: `[^;]*)`.
   Test: `tests/http/response_parser_spec.lua` ("keeps a Set-Cookie header
   with an empty value…").

6. **Large-body dump filenames collided on macOS** —
   `lua/poste-http/http/format/util.lua` built dump names with
   `strftime("%6N")`, a glibc extension that macOS renders as a literal
   `6N` (verified: `vim.fn.strftime('%6N')` → `6N`). Names collapsed to
   second precision, so two large responses finishing in the same second
   overwrote each other's dump files. Also made `save_body_to_file` return
   lines instead of nil when the dump write fails (callers `ipairs()` the
   result; a nil return crashed the render pipeline).
   Fix: millisecond suffix from `uv.hrtime()`, matching the sibling call
   sites in `format/body.lua` / `format/verbose.lua`. Tests:
   `tests/http/disposition_download_spec.lua` (filename pattern +
   no-literal-`6N`, write/metadata contract).

## Bugs found, not fixed (rationale)

- `response.ok = status < 400` stamps `ok=true` for status 0 in
  `parse_response`. Looks wrong but is pinned by `tests/http/response_spec.lua`
  ("keeps the historical success verdict for legacy status 0") and documented
  in `lua/poste-http/http/response.lua` — changing it would flip behavior for
  legacy status-0 stubs across import/run paths. Needs a deliberate design
  decision, not a drive-by fix.
- `parse_headers_file` keeps only the LAST header block of a redirect chain,
  so `Set-Cookie` headers set by intermediate 3xx hops are lost (curl `-D`
  dumps every hop). Session-cookie handling across redirects would want
  per-hop collection; that's a feature-sized change.
- `redirect_count` in `parse_response` greps the verbose log for
  `N redirects`; modern curl does not emit such a line, so the metadata is
  usually "0". Cosmetic; the right fix is `--write-out %{num_redirects}`
  into a temp file, which touches the curl argv contract.
- `curl.lua` (paste-curl) does not support `--header=X`/`-H'X: y'` combined
  forms, `--data-urlencode`, or `-d@file`, and drops `X-Custom:` headers with
  an empty value. Edge-case importer gaps; each needs its own spec.
- `ftplugin/poste_http.vim` kulala cleanup and completion setup run on every
  `.http` buffer open; harmless but it duplicates `plugin/poste.lua`-adjacent
  concerns (see smells).

## Smells (documented, not refactored)

- **Copy-paste blocks between `plugin/poste.lua` autocmd and the
  already-loaded-buffers loop** (lines ~40-90): the CursorMoved/BufDelete
  group setup appears twice. Extract a `buffer_setup.attach_boundary(buf)`.
- **`plugin/poste.lua` BufEnter sets `vim.wo.winbar`** for the whole window
  and never restores/clears it when a non-.http buffer is shown in the same
  window; the winbar also comes from `ui/winbar` elsewhere — unify through
  `ui/winbar`.
- **Dead/heuristic code in `parse_response`** partially removed (the `from`
  host heuristics); `redirect_count` grep remains (see above).
- **luacheck residue**: `run.lua:524` re-`require`s `import_mod` (shadowing
  the top-level), `run.lua:763` `ctx` shadowing in nested callbacks,
  `copy.lua`/`import.lua` shadow an upvalue named `vars`, `item_builder.lua`
  re-declares `KIND_VARIABLE` twice, `request_deps.lua:192` has an unused
  function, several intentional empty-if branches (`cache.lua:607`,
  `copy.lua:240`) would read better as `goto continue`-style skips.
- **`vars.lua:63`** `local next = result:gsub(...)` shadows the global
  `next` inside `substitute` (works today, dangerous tomorrow).
- **`form_data.lua:36`** uses `gsub(pattern, value)` with a generated value
  as the replacement string — safe while values are digits/hex/dashes, but
  a `%` in a generated value would be interpreted as a capture reference;
  escape replacements (`value:gsub("%%", "%%%%")`).
  *(Fixed 2026-09-06: substitution extracted to `form_data.substitute_magic_vars`
  with a function replacement so values stay literal; regression tests in
  `tests/http/form_data_spec.lua`.)*
- **`load_env_vars_with_lines`** brace-counts `{`/`}` across env.json values,
  so a `{` inside a value shifts the section end. Heuristic line-mapping only;
  fine unless env values carry braces.
- **`json_pretty` does not escape object keys** (`format/util.lua`); keys
  containing quotes/newlines (possible from decoded JSON) produce invalid
  pretty output.
- **`describe.lua:get_node_text`** indexes `lines[sr + 1]` without a bounds
  check; a node range past the source would error. Guarded by parser
  correctness today.
- **`tests/run.sh` truncation risk**: `PlenaryBustedDirectory … -c "qa"`
  exits before async spec output flushes on slow machines, so a run can end
  early with exit 0 (AGENTS.md's "check the spec-file count" rule mitigates;
  consider asserting the file count in run.sh itself).
