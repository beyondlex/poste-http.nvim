## Bug fixed in the gRPC feature (commit `50e3c9a`)

- **`grpc_proto.index_key` read a nonexistent `st.stat` wrapper** — real
  `vim.uv.fs_stat` returns the stat table FLAT (`st.mtime = {sec, nsec}`),
  but the key folded `st.stat.mtime`, which is always nil. Proto file
  edits therefore never changed the cache key: the documented
  "editing a proto invalidates the index" mechanism was dead code and a
  stale index survived until the buffer's cache was dropped. The spec's
  stub had been written in the wrong (wrapped) shape, which is why it
  passed. Fixed to read the flat shape (wrapped still accepted); two
  regression tests: the flat shape changes the key, and a real temp file's
  mtime is folded (not the "missing" sentinel).

## Findings documented, not fixed

- **`script_sandbox.build_sandbox_env` exposes full `os` and `io` to user
  scripts** — `os.execute`, `io.open`, `io.read` are reachable from
  `> {% %}` / `< {% %}` scripts. `.http` files are routinely shared
  (checked into repos, imported from Postman), and pre-scripts run on
  execution, so a shared file can shell out. The poste-mq family member
  explicitly excludes os/io from its sandbox. Tightening this is a
  product decision (existing scripts may legitimately use `os.date` or
  read a fixture): suggested shape is a curated `os` (date/time/clock/
  getenv) and dropping `io` (file_include already covers file input).
  *(Fixed 2026-09-07: adopted the suggested shape — curated `os`
  (date/time/clock/getenv), no `io`; orchestration.lua now builds its
  env via `build_sandbox_env` (gains `md5`), and script completion
  (`data.lua`) no longer suggests the removed members.)*
- **`http/orchestration.lua` hand-rolls its sandbox env** instead of
  calling `script_sandbox.build_sandbox_env` — same stdlib list but no
  `md5`/`select`, and the two lists WILL drift. Refactor needs care (the
  orchestration env adds coroutine-driven `client.run`, `print`), so it
  is flagged, not smuggled in.
  *(Fixed 2026-09-07: orchestration builds the base env via
  `build_sandbox_env` and layers its own `client`/`print`/`assert` on
  top.)*
- **`ws_session.open_ui` accumulates `BufWipeout`/`BufDelete` autocmds**
  on the response buffer (one per interactive session, never cleared).
  Behaviorally benign — the handler `M.close()` is idempotent and closing
  the buffer while a session is live is the desired behavior — but it
  should delete the previous autocmd per session.
- `import.lua`'s module/variable `vars` shadowing (4 sites) re-verified
  safe today: the only module-level `vars.` use (line 513) is in a
  function with no shadowing local. Fragile pattern, already on the
  smell list.
