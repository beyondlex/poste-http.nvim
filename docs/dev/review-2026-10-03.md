## Fixed this round

1. **`assertions.format_assertions` crashed on shape-drifted results** —
   the assertions tab also renders HISTORY entries, whose fields come from
   persisted JSON (hand-editable, written by older versions, or truncated
   by a crash). A string `passed`/`failed` raised "number expected, got
   nil" out of string.format mid-render. Now normalized once at the top
   (numeric coercion, table guards), and a non-table test entry renders as
   failed-unknown (`✘ ?`) — drift is not evidence of a pass. Specs: shape
   drift + well-formed-identical rendering in `assertions_spec`.

2. **`history.load` shipped drifted inner fields to the views** — entries
   with a numeric id passed the load filter, but a `response = 42`,
   `script_logs = "x"`, or `assertion_results = 7` from the same corrupt
   file then raised inside `format_view`. Load now drops non-table values
   for those three fields at the disk boundary — the entry keeps its
   name/time in the list while the detail views degrade. Spec in
   `history_persistence_spec`.

3. **All three spec importers crashed on malformed specs** (14 distinct
   crash shapes from 27 probe inputs). Root cause: `vim.json.decode` turns
   JSON null into the `vim.NIL` userdata, which `== nil` checks and
   `or {}` fallbacks do NOT catch — `spec.info.name` on a null info raised
   "attempt to index a userdata value" through Postman; scalar
   `security`/`parameters`/`urlencoded`/`query` lists raised
   ipairs-on-a-string. OpenAPI happened to type-check its path items; the
   other entry points had no such treatment. Fixes:
   - `import_parser.read_spec` strips vim.NIL recursively at the single
     decode boundary (`util.clean_nil`) — every importer now sees plain
     nils; `make_filename` accepts non-string titles.
   - `import_postman`: `parse_item`/`parse_url`/`parse_body`/
     `collect_variables` type-check list fields; a drifted raw body
     imports as empty instead of crashing `generate_http_block`'s concat.
   - `import_swagger`: `security`/`securityDefinitions`/`parameters`
     type-checked.
   Specs: malformed collections in `import_postman_spec`, drifted
   sections + the read_spec null contract in
   `import_openapi_swagger_spec`.

4. **Both `json_pretty` implementations emitted bare `inf`/`nan`** —
   `vim.json.decode` accepts `1e999` and hands back `math.huge`; tostring
   produced an invalid-JSON token that broke every later parse of the
   formatted body (jq, treesitter, filters). Non-finite numbers now encode
   as `null` (the jq/JS convention) in `format/util.json_pretty` and
   `format_file`'s private copy. Specs pin both renderers + a decode
   round-trip.

## Recorded (uncertain / intentional)

- **`diagnostics.lua` treesitter query style** — `query:iter_matches`
  consumed via `pairs(match)` with numeric capture ids matches the older
  nvim API; on newer builds the loop may silently yield nothing (parse is
  pcall'd, so the worst case is "no diagnostics", never a crash). If the
  syntax-error squiggles ever stop working, start there.
- **`format_file` body detection splits plain-text bodies** at lines that
  look like request lines (`WARNING foo`) — documented tradeoff of the
  line-heuristic formatter; JSON bodies (the common case) are unaffected.
- **`format_file` placeholder collision** — a body literally containing
  `__POSTE_VAR_Q_1__` could be rewritten by the `{{var}}` restore pass.
  Pathological input only.
- **`format/util.human_size` accepts non-numbers** — every current caller
  passes a length it computed itself; a defensive `type` check would be
  dead code today.
- **Script sandboxes still allow infinite loops** (`while true do end`
  hangs nvim; no instruction-budget precedent in the family) — self-inflicted,
  recorded, unchanged from the poste-mq 10-02 stance.

## Lessons (this round)

- **`vim.NIL` is not nil at every `or {}` and `== nil` boundary.** JSON
  null decodes to userdata; only a recursive clean at the decode boundary
  (or `type(x) == "table"` checks) sees through it. One clean call in
  `read_spec` replaced 14 crash sites across three importers — normalize
  at the boundary, not at each use.
- **Anything rendered from persisted JSON must be shape-checked at load.**
  History entries are user-editable files on disk; every field can be any
  JSON type. Drop drifted fields at the boundary (keep the entry), guard
  the renderer anyway — two layers because the file format and the views
  evolve on different schedules.
- **A number that survived JSON decode is not necessarily finite.**
  `1e999` decodes to `math.huge`; any Lua-side JSON re-encoder needs the
  non-finite branch, not just vim.json.encode's error.
